# Тестове завдання: сервіс бронювання переговорних кімнат

**Рівень:** Junior / Strong Junior
**Час:** 8 год — основна частина + до 2 год — додаткові завдання
**Формат:** робота з **Claude Code дозволена й очікується**. Ми оцінюємо не тільки результат, а й те, як ти керуєш AI: ставиш задачі, перевіряєш код, ловиш помилки й розумієш кожен рядок, який здаєш.

---

## Контекст

В офісі є кілька переговорок, і люди постійно бронюють їх «наслоєм». Потрібен бекенд-сервіс, через який співробітники бронюють кімнати, бачать вільні слоти й скасовують свої бронювання.

## Стек

- **Рекомендовано:** Node.js + TypeScript (NestJS / Fastify / Express) + PostgreSQL
- **Можна:** Python (FastAPI) + PostgreSQL
- ORM / query builder — на твій вибір (Prisma, TypeORM, Drizzle, Knex, SQLAlchemy…)
- Тести: Jest / Vitest / pytest
- Запуск: `docker compose up` має піднімати застосунок і БД

## Автентифікація (спрощена)

Справжня авторизація не потрібна. Користувача визначаємо за заголовком `X-User-Id` (будь-який непорожній рядок). Без заголовка — `401`.

## Основні завдання (8 год)

> Години — орієнтир, а не жорсткий ліміт. Якщо щось не встигаєш, краще зробити менше, але якісно, і описати в README, що лишилося.

### 1. Підготовка проєкту та CLAUDE.md — 0.5 год

- Ініціалізуй репозиторій, налаштуй лінтер і форматер.
- Створи `CLAUDE.md` з правилами проєкту для Claude Code: стек, структура папок, як запускати тести, code style, заборони (наприклад, «не змінювати міграції, які вже є»).
- Перед кодом попроси Claude скласти план і збережи його в `docs/PLAN.md`. Можна правити його вручну.

**Готово, коли:** у репо є `CLAUDE.md`, `docs/PLAN.md`, проєкт стартує, лінтер проходить.

### 2. Модель даних і міграції — 1 год

Сутності:

- **Room:** `id`, `name` (унікальна), `capacity` (> 0), `createdAt`
- **Booking:** `id`, `roomId`, `userId`, `title`, `startAt`, `endAt`, `status` (`active` / `cancelled`), `createdAt`

Вимоги:

- Міграції, а не `synchronize: true` / автоматичне створення таблиць.
- Seed-скрипт: 3–4 кімнати й кілька бронювань.
- Час зберігаємо в **UTC**.

**Готово, коли:** `npm run migrate && npm run seed` (або аналог) створює схему й дані з нуля.

### 3. CRUD кімнат — 0.5 год

- `POST /rooms`, `GET /rooms`, `GET /rooms/:id`
- Валідація вхідних даних, помилка `409`, якщо назва вже зайнята.
- Формат помилок однаковий для всього API, наприклад `{ "error": { "code": "...", "message": "..." } }`.

### 4. Створення бронювання (бізнес-логіка) — 2 год

`POST /bookings` → `{ roomId, title, startAt, endAt }`

Правила:

1. `startAt` / `endAt` приходять в ISO 8601 **зі зміщенням** (наприклад `2026-11-20T10:00:00+02:00`). Без зміщення — `400`.
2. `startAt < endAt`, бронювання не в минулому.
3. Тривалість — від **15 хв** до **4 год**.
4. Час кратний **15 хвилинам** (10:00, 10:15, 10:30…).
5. Робочі години — **08:00–20:00 за Києвом (`Europe/Kyiv`)**, будні дні (пн–пт). Бронювання має повністю влазити в робочий час.
6. **Жодних перетинів** з активними бронюваннями тієї ж кімнати. Бронювання «впритул» дозволене (10:00–11:00 і 11:00–12:00 — ок).
7. **Конкурентність:** якщо два запити на той самий слот приходять одночасно, успішним має бути рівно один, другий отримує `409`. Перевірки «SELECT, потім INSERT» без захисту недостатньо.

**Готово, коли:** усі правила покриті тестами, а помилки повертають зрозумілі коди (`400` / `404` / `409`).

### 5. Скасування та список бронювань — 1 год

- `DELETE /bookings/:id` — soft-delete (`status = cancelled`).
  - Скасувати може тільки автор (`403` для інших).
  - Бронювання, яке вже почалося або минуло, скасувати не можна.
- `GET /bookings?roomId=&from=&to=&mine=true&page=&limit=`
  - Фільтри комбінуються.
  - Пагінація, у відповіді є `total`.
  - Сортування за `startAt`.

### 6. Вільні слоти — 1 год

`GET /rooms/:id/availability?date=2026-11-20`

- Повертає список **вільних інтервалів** у робочий час цього дня (за Києвом), склеєних між собою, наприклад:
  `[{ "from": "08:00", "to": "10:00" }, { "from": "11:30", "to": "20:00" }]`
- Скасовані бронювання не враховуються.
- Вихідний день → порожній список.

### 7. Тести — 1.5 год

- Unit-тести на валідацію часу (кратність, робочі години, тривалість, таймзона).
- Інтеграційні тести API на реальній БД (testcontainers або окрема БД у docker compose).
- Обовʼязковий тест на **конкурентність**: N паралельних запитів на один слот → рівно 1 успішний.
- `npm test` запускається однією командою.

### 8. README та AI_LOG — 0.5 год

- `README.md`: як запустити, як прогнати тести, приклади запитів (curl), що не встиг і чому.
- `AI_LOG.md` (**обовʼязково**), 1–2 сторінки, не більше:
  - 3–5 ключових промптів, які ти давав Claude Code;
  - **де AI помилився** і як ти це помітив (тест, ревʼю, ручна перевірка);
  - що ти свідомо переписав сам;
  - одне рішення, з яким ти не погодився б, якби AI запропонував його без пояснень.

Будь готовий:

- пояснити **будь-який рядок** коду, зокрема написаний AI;
- наживо, без AI, внести невелику зміну (наприклад, змінити робочі години або мінімальну тривалість);

## Критерії оцінки

| Критерій | Вага | Junior — достатньо | Strong Junior — очікується |
|---|---|---|---|
| Бізнес-правила (п.4–6) | 30% | Більшість правил працює, є дрібні діри на краях | Усі правила, включно з таймзоною й «впритул» |
| Конкурентність | 10% | Транзакція + блокування / розуміє проблему | Обмеження на рівні БД (exclusion constraint / `SELECT ... FOR UPDATE`) + тест, що це доводить |
| Тести | 20% | Основні сценарії покриті | Edge cases + інтеграційні тести на реальній БД + тест на гонку |
| Структура коду | 15% | Код читається, логіка не вся в контролерах | Чіткий поділ шарів, бізнес-правила тестуються окремо від HTTP |
| Робота з Claude Code | 15% | Є `CLAUDE.md` і чесний `AI_LOG` | Добре налаштований `CLAUDE.md`, видно ітерації, знайдені та виправлені помилки AI |
| README / запуск | 10% | Запускається за інструкцією | `docker compose up` з нуля, зрозумілі приклади |

**Червоні прапорці:**

- не може пояснити свій код на захисті;
- `AI_LOG` порожній, формальний або «AI ні разу не помилився»;
- тести є, але нічого не перевіряють (наприклад, `expect(res).toBeDefined()`);
- один коміт на весь проєкт;
- закомічені `.env` із секретами або `node_modules`.

## ⚠️ ДЛЯ РЕВʼЮЕРА — видалити перед відправкою кандидату

Місця, де Claude Code (та й люди) найчастіше помиляються. Саме тут видно, чи кандидат перевіряв код, а не просто приймав його:

1. **Перетин інтервалів.** Правильна умова: `existing.start < new.end AND existing.end > new.start`. Типові помилки: `<=` (ламає «впритул») або перевірка лише того, чи попадає `start` в інтервал (пропускає бронювання, що повністю охоплює інше).
2. **Таймзона.** Робочі години перевіряють у UTC (08:00–20:00 UTC ≠ Київ) або через `new Date().getHours()` у локальній зоні сервера. У Docker зона сервера зазвичай UTC, тож локально «працює», а в контейнері — ні.
3. **Перехід на літній/зимовий час.** Зміщення Києва +02:00 / +03:00. Якщо в коді захардкоджено `+2`, тест на дату в липні впаде. Хороший кандидат використовує бібліотеку (`date-fns-tz`, `luxon`, `zoneinfo`).
4. **Конкурентність.** Найчастіше: SELECT на перетин → INSERT без блокування. Перевірити: попросити показати тест з `Promise.all` на 10 запитів. Найкраще рішення в Postgres — `EXCLUDE USING gist (room_id WITH =, tstzrange(start_at, end_at) WITH &&) WHERE (status = 'active')`.
5. **Скасовані бронювання** враховуються при перевірці перетину або у вільних слотах.
6. **Вихідні:** дату визначають у UTC, а не за Києвом (бронювання в пн 01:00 за Києвом — це ще неділя в UTC).
7. **Availability:** не склеює суміжні вільні інтервали або повертає слоти поза робочим часом.
8. **Пагінація:** `total` рахується без урахування фільтрів.
9. **Скасування:** перевіряють `endAt < now` замість `startAt <= now` (дозволяє скасувати бронювання, яке вже йде).

**Питання на захисті для strong junior:**

- «Що буде, якщо запустити два інстанси сервісу за балансувальником? Твій захист від гонки ще працює?» (in-memory lock — ні, constraint у БД — так)
- «Як змінити робочі години без деплою?»
- «Покажи місце, де Claude запропонував щось погане, і чому ти це прибрав.»
